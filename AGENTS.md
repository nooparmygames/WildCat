# AGENTS.md

This is the maintained project guide for Codex, ChatGPT and other coding agents in this checkout.
Read [the project memory index](docs/project-memory/MEMORY.md) when starting work and follow
its task links. Keep confirmed decisions here and durable milestones in project memory.
`CLAUDE.md` imports this file for compatibility.

WildCat is a game backend being prepared for open-source release under the MIT license (see
`LICENSE`, NoOpArmy Softworks). It is built on Microsoft Orleans (virtual actors) and comes with a
Unity client SDK and a web admin panel. The code started life in 2019 to 2021 as the "Apadana"
platform (Orleans 3.4.3, net5.0, MongoDB, PlayFab, CafeBazaar IAP, Persian UI). The legacy code
was copied here on 2026-09-30 with a fresh git history and its secrets removed. The old
repository's history still contains an AWS access key, a PlayFab developer secret and an SMTP
password; those credentials must be rotated by the owner regardless of what happens here.

## Toolchain and commands

- .NET SDK 10.0 is installed. Node and npm are installed for the panel. Docker is available.
  No database server is installed locally; use Docker. In a fresh cloud container without
  `dotnet`, install it with `apt-get install -y dotnet-sdk-10.0` (the dot.net install script
  host is blocked by the proxy; the Ubuntu archive is not). The Docker daemon may need starting
  (`dockerd > /tmp/dockerd.log 2>&1 &`), and Docker Hub pulls can hit the anonymous rate limit
  (429); `mirror.gcr.io/library/postgres:17` is the same image.
- Everything targets net10.0 on Orleans 10.3.1 except `WildCat.Protocol` (netstandard2.1 with
  C# 9, no nullable annotations and no package references, because Unity 6 compiles the same
  source). Shared settings live in `backend/Directory.Build.props` and package versions in
  `backend/Directory.Packages.props` (central package management):

```bash
dotnet build backend/WildCat.sln
```

- After changing anything in `backend/WildCat.Protocol`, regenerate the SDK copy (the
  `ProtocolSyncTests` fail until you do; never edit the copy by hand):

```bash
tools/sync-protocol.sh          # Windows: pwsh tools/sync-protocol.ps1
```

- Tests use xUnit on an `InProcessTestCluster` shared by one collection fixture. They are slow
  (100-player matchmaking loads, multi-second sleeps), order dependent within a collection, and
  some wait forever on failure, so pass `--blame-hang-timeout 4m` for full runs. Run one class
  at a time when iterating:

```bash
dotnet test backend/WildCat.Tests/WildCat.Tests.csproj --filter "FullyQualifiedName~LeaderBoardTests"
```

  The fixture registers `CapturingEmailSender`, so tests can read the emails the grains send.
  The PostgreSQL provider tests (`PostgreSqlStorageTests`, `PostgreSqlHostTests`) are skipped
  unless `WILDCAT_TEST_POSTGRES` holds a connection string to a database with the Orleans scripts
  from `deploy/postgres` applied; each run uses its own ClusterId and ServiceId:

```bash
WILDCAT_TEST_POSTGRES="Host=localhost;Port=5432;Database=wildcat;Username=wildcat;Password=..." \
  dotnet test backend/WildCat.Tests/WildCat.Tests.csproj --filter "FullyQualifiedName~PostgreSql"
```

- Run the host: one process runs the silo and the WebSocket gateway at `/ws` on port 5000.
  Configuration is in `backend/WildCat.Host/appsettings.json`, which holds the structure with
  empty values; real values come from user secrets (`dotnet user-secrets --project
  backend/WildCat.Host set ...`) or environment variables (`__` for `:`). The sections:
  - `WildCat:Orleans` (`OrleansHostingOptions`): `Provider` is `Memory` (default: localhost
    clustering, memory grain storage, in-memory reminders, all lost on exit; outside Development
    the host logs a warning) or `PostgreSQL` (ADO.NET clustering, grain storage for "Default",
    "blob" and "PubSubStore", and reminders, invariant `Npgsql`). Also `ClusterId`
    (`wildcat-dev`), `ServiceId` (`wildcat`, keys all stored data, never change it), `SiloPort`
    (11111), `GatewayPort` (30000) and `AdvertisedHost` (PostgreSQL only; empty advertises the
    first non-loopback IPv4 address, and the silo listens on every address). Streams are memory
    streams (`AddGameStreams()`) with either provider.
  - `ConnectionStrings:WildCat`: the PostgreSQL connection string. The host refuses to start
    when the provider is PostgreSQL and it is empty.
  - `WildCat:Seed` (`SeedOptions`): developers and games (plus leaderboard "l1" per game)
    created at startup by `SeedHostedService` when missing. Only `appsettings.Development.json`
    has one: developer `11111111-1111-1111-1111-111111111111` with game
    `22222222-2222-2222-2222-222222222222` (placeholders for local clients and smoke tests).
  - `WildCat:Email` (`EmailOptions`): SMTP settings. With `SmtpHost` and `FromAddress` set,
    `SmtpEmailSender` sends; otherwise `LoggingEmailSender` logs the code at Warning. Texts are
    in `WildCat.Grains/Resources/EmailTexts.resx`.
  - `Gateway` (`GameGatewayOptions`: `MaxMessageBytes`, `AllowedOrigins`, `AuthAttemptBurst`,
    `AuthAttemptsPerMinute` (per connection), `AuthAttemptsPerAddressBurst` (30, 0 turns it off)
    and `AuthAttemptsPerAddressPerMinute` (30) (per client address over all its sockets; the
    forwarded address, IPv6 per /64, loopback not limited), `OutboundQueueCapacity` (1024 frames)
    and `OutboundQueueBytes` (8 MiB) for a connection's outbound queue, `RelayQueueBytes` (4 MiB)
    for its relay queue, `MaxConcurrentRequests`) and `ForwardedHeaders` (`KnownProxies` as
    addresses, `KnownNetworks` as CIDR ranges; loopback only by default). String length limits
    for what clients send are fixed in `WildCat.Protocol/Codec/WireLimits.cs` (with the collection
    count limits the decoder enforces) and checked by the gateway's `InputLimits`.

```bash
dotnet run --project backend/WildCat.Host
```

  Against PostgreSQL (a database created with the scripts in `deploy/postgres`, for example the
  `postgres` service of the compose file):

```bash
WildCat__Orleans__Provider=PostgreSQL \
ConnectionStrings__WildCat="Host=localhost;Port=5432;Database=wildcat;Username=wildcat;Password=..." \
  dotnet run --project backend/WildCat.Host
```

  When other hosts run on the same machine, move the ports: `--urls http://localhost:5001`,
  `WildCat__Orleans__SiloPort` and `WildCat__Orleans__GatewayPort`.
- CI is `.github/workflows/ci.yml` (GitHub Actions, on every push and pull request; the README
  describes it). Job `backend` runs the commands above in Release (`dotnet build -c Release`,
  then `dotnet test -c Release --no-build --blame-hang-timeout 4m --logger trx`) with
  `WILDCAT_TEST_POSTGRES` pointing at a PostgreSQL 17 service container that got the
  `deploy/postgres` scripts, so the PostgreSQL tests must pass there too. Job `compose` copies
  `.env.example` to `.env`, makes the two edits README quick start B asks for (a password and an
  `openssl rand -base64 32` signing key) and runs `docker compose config -q`, so keep the
  quick start, `.env.example` and `compose.yaml` in step. Job `panel` runs
  `npm ci`, `lint`, `test` and `build` on Node 22; job `docker` builds the host image from
  `compose.yaml`'s context. Actions are pinned to major versions. Check the workflow after
  editing it with actionlint at the repository root (needs Go):

```bash
go install github.com/rhysd/actionlint/cmd/actionlint@latest && "$(go env GOPATH)/bin/actionlint"
```
- Use an installed Unity 6 LTS Editor for package import, compilation, editor tools and sample
  checks when authorized. The previous cloud session had no Unity installation; that was an
  environment limitation, not a project rule. On this Windows machine Unity 6000.0.80f1 is
  installed with Web and Windows modules. Plain .NET tests also cover the engine-free SDK:
  Runtime/Protocol and Runtime/Core against the real gateway and in-process cluster, plus
  WildCat.Sdk.CoreCheck (netstandard2.1, C# 9, warnings as errors). Both are in the solution
  and CI. See project memory for the latest actual Editor verification and its limitations.

```bash
dotnet test unity-sdk/Tests/WildCat.Sdk.Tests/WildCat.Sdk.Tests.csproj
```

## How the system fits together

Read `docs/legacy-backend-notes.md` for the full picture. The short version:

- Grains live in `backend/WildCat.Grains`, interfaces and state classes in
  `backend/WildCat.Interfaces`.
  Player, Session, Developer, RelayServerGame, RelayServerMatchMaker, PlayerFriendList,
  PlayerChallengeHandler, LeaderBoard, PlayerInventory, PlayerStorage, ScriptEventCompiler and
  the id-map grains are the core. `Game`/`MatchMaker` and the TimedExecuter subsystem were
  removed in roadmap step 2.
- A developer (publisher) owns games. A client initializes a session with developer key plus
  game key, receives a Guid ticket, logs in as a player, and sends every later message with the
  ticket.
- The gateway (`backend/WildCat.Gateway`, see `docs/gateway.md`) runs inside the silo process
  and uses the silo's `IClusterClient`. `WebSocketConnection` reads frames and writes queued ones
  from a single writer; `MessageDispatcher` decodes them through `WireCodec` (the one serializer
  boundary, `docs/wire-protocol.md`), relays game messages in order, checks the session each
  route requires and runs one handler per message type (`Handlers/<group>/`, found by
  reflection). Server events come back through Orleans memory streams (provider `game`, ids built
  by `WildCat.Interfaces/StreamNames.cs`) and go into the connection's outbound queue. The old
  one-class gateway (`FrontEndServer`) is gone since step 6b.
- Matches are relay games: the server tracks membership and properties and forwards opaque
  byte arrays between players; it never simulates the game. Matchmaking is per game mode with a
  time-based relaxation schedule.
- Developers can attach C# scripts to named events; they run in a Roslyn sandbox on the silo
  and reach the server through the `WildCat` global (`WildCat.Scripting.WildCatScriptApi`).
- Orleans 3.x allowed call chain reentrancy by default and the legacy grains depend on it
  (A calls B calls A). `WildCat.Grains/CallChainReentrancyFilter.cs`, registered through
  `AddLegacyCallChainReentrancy()` in `WildCat.Grains/SiloBuilderExtensions.cs`, restores that for
  every call. Replace it with targeted `RequestContext.AllowCallChainReentrancy()` calls at the
  known cycles before removing it. The same extensions class holds the provider setup
  (`AddWildCatProviders`, split into `AddWildCatClustering` and `AddWildCatStorage`) and the
  stream setup shared by the host and the tests.
- Account emails go through `IEmailSender` (WildCat.Interfaces), injected into the Player grain;
  `AddWildCatEmail` in WildCat.Grains picks the SMTP or the logging implementation.

## Decisions (confirmed by the owner on 2026-09-30)

- Name: WildCat everywhere. Done in step 3 (commit "Rename the project to WildCat"): namespaces,
  `ApadanaMessageBase`/`ApadanaMsgType` (now `WildCatMessageBase`/`WildCatMsgType`), the
  `ScriptingAPI.Apadana` script object (now `WildCatScriptApi`, script global `WildCat`), editor
  menus, solution and project names. New code uses the WildCat names only.
- Orleans 10 on .NET 10, following `.agents/skills/orleans/reference/migration-3x.md`.
- Storage: PostgreSQL through the official ADO.NET packages for clustering, grain state and
  reminders. Memory providers in Debug and tests. No MongoDB, no Azure, no Redis.
- PlayFab: removed entirely. Delete `PlayfabManager`, `IBackendStorageServer`, the PlayFab
  branches in Player, PlayerStorage, PlayerFriendList, PlayerChallengeHandler, TimedExecuter,
  the `PlayFabAllSDK` package, `IsPlayfabRun` flags, the `titleId|playfabId` key format and the
  SDK's `InvitationType.PlayfabId`.
- CafeBazaar: removed entirely (grains, gateway handler, SDK call, panel tab). No other store
  receipt verification replaces it for now.
- Secrets and personal data: none in code or sample config, ever. SMTP, database and any
  future API keys come from configuration, user secrets or environment variables. Test data
  uses example.com addresses and placeholder GUIDs.
- Wire protocol: keep the one-binary-message-per-WebSocket-frame format the SDK implements,
  but fix it: explicit message ids, no ticket in relayed frames, the serialization bugs in
  `docs/wire-protocol.md`, invariant DateTime encoding, one protocol source shared by server and
  SDK. The owner wants to move to a different format later (MessagePack was judged too large a
  payload), so keep the protocol behind one serializer boundary.
- Admin: ASP.NET Core minimal REST API co-hosted with the silo (JWT bearer auth, OpenAPI), and a
  React + TypeScript SPA (Vite) as the panel. The endpoint list in `docs/legacy-admin-panel.md`
  is the starting contract.
- Tenancy: keep developers, games, developer secrets and per-game scoping. Drop billing:
  delete `AccountingSystem`, `DeveloperInvoiceCollection`, `InvoiceUtility`, the call and
  message counters in `Session`, the accounting endpoints and the dashboard counters in the
  panel spec. Usage metrics come back later through OpenTelemetry if needed.
- Script events: keep and port as is, then harden (per-player data scoping, real timeouts,
  cluster-wide compiled cache, diagnostics surfaced to the panel).
- Unity SDK: target Unity 6 LTS only, shipped as a UPM package (`package.json`, asmdef,
  Runtime/Editor/Samples~ layout). Done in step 8 as `com.noopsoftworks.wildcat`.
- Email: keep email login, activation and password reset with SMTP settings in configuration
  and a pluggable sender that logs the code when SMTP is not configured.
- No legacy data to migrate; state shapes can change freely.
- Deployment: Docker Compose first (PostgreSQL plus the WildCat host). Kubernetes later.
- Tests: port the existing suite to `InProcessTestCluster` as a safety net during the port,
  then replace it feature by feature with tests that use unique grain keys and bounded waits.
- All text a person reads (docs, comments, commit messages, UI strings) is plain ASCII in a
  natural voice; English is the default UI language, translations live in resource files.

## Working rules for this repo

- Use the `orleans` skill for anything touching grains, hosting, storage, streams or tests. Its
  ten rules in `SKILL.md` are the review checklist.
- Every type crossing a grain call or stored as state gets `[GenerateSerializer]`, `[Id]` and
  `[Alias]` once the port starts. No `.Wait()`/`.Result`/`ConfigureAwait(false)` in grains.
- Grain state goes through a constructor-injected `[PersistentState(name, provider)]
  IPersistentState<T>`, never `Grain<T>`, with a state name of its own added to
  `WildCat.Grains/GrainStateNames.cs`: the ADO.NET storage keys rows by grain key and state name
  only, so two grain classes with the same key and state name overwrite each other in
  PostgreSQL. `GrainStateNameTests` enforces it.
- Grain interface names start with `I` and files match the type name (`IPlayer.cs`, not
  `iPlayer.cs`). Fix legacy names when a file is otherwise being edited, in a separate commit.
- New tests use unique grain keys per test and never wait without a timeout.
- Do not add connection strings or credentials to any checked-in file. `appsettings.json` holds
  structure with empty values; real values come from user secrets or environment variables.
- Before deleting legacy code, check `docs/legacy-backend-notes.md` for the bug list attached
  to it; some "bugs" are behaviors the SDK relies on.

## Writing and handoff

Use ASCII for human-readable text, except content that requires another language or Unicode
fixtures. Use straight quotes and plain hyphens. Write naturally, keep concrete examples, and
avoid filler, repetitive bold lead-ins, and a heading above every short paragraph. Documentation
should explain a concept's job and its consequences, with technical claims checked against
source. Do not compress several conditions into a sentence that needs to be read twice.

After substantive work, give a self-contained recap of the full request: what changed and why,
what was tested and the result, and any unfinished work or limitations. Link the main files and
state whether changes were committed, pushed or published. Ordinary questions need a direct
answer; interrupted work must be described as incomplete.

Product documentation explains how to use WildCat. Keep test counts, review history, agent
activity and delivery reports in project memory or chat recaps. Retain support limits and
troubleshooting steps where they affect the reader. Introduce each concept through its job,
then explain the relevant behavior and consequence. Preserve worked examples and exact API
names; split overloaded sentences instead of turning explanations into terse fragments.
Roadmaps describe planned features directly, without approval history or competitor comparisons.
