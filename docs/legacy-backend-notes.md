# Legacy backend notes: grains, flows, dependencies, known bugs

Survey of `backend/` as copied from the Apadana 2 repository on 2026-09-30 (Orleans 3.4.3, net5.0,
about 18,000 lines), updated after roadmap step 2 removed PlayFab, CafeBazaar, billing and the
dead subsystems, after step 4 fixed the bugs marked "Fixed in step 4" in the bug list, and after
step 5 added the PostgreSQL providers and the configuration model, and after step 6 split the
gateway and moved the protocol behind one codec (docs/gateway.md, docs/wire-protocol.md). Removed code keeps a short note
here (see "Removed in step 2" at the end) so bug numbers and history stay readable. CLAUDE.md
describes the Orleans 10 host from step 1. Read this before touching a grain. File names are
relative to `backend/`. Line numbers refer to the copied files.

Paths and names follow the WildCat rename from roadmap step 3; the table below gives each
project's legacy name.

| Project (legacy name) | Role |
|---|---|

Environment facts that apply everywhere: every stateful grain injects
`[PersistentState(name, provider)] IPersistentState<T>` with a state name of its own
(`WildCat.Grains/GrainStateNames.cs`); only `LeaderBoard` uses the "blob" provider, every other
grain "Default". Until the step 5 review the grains derived from `Grain<T>`, which stores every
class under the state name "state"; the ADO.NET provider keys rows by service id, grain key and
state name only, so grain classes sharing a key (Developer and DeveloperStorage, PlayerFriendList
and PlayerChallengeHandler, a leaderboard and a chunk of another) overwrote each other in
PostgreSQL. `GrainStateNameTests` keeps the names unique. The ADO.NET storage writes JSON with
every value, defaults included (`SiloBuilderExtensions.WriteDefaultValues`); the Orleans default
left out false and 0, so values a constructor sets otherwise (a game mode's
`FinishGameWithOneDisconnect`, a leaderboard's `AcceptBetterScoresOnly`) came back wrong after a
reactivation. `WildCat:Orleans:Provider` decides what backs
the storage names "Default", "blob" and "PubSubStore": memory storage for `Memory` (the default,
also used by the tests), or ADO.NET storage in PostgreSQL for `PostgreSQL`, which also puts
clustering and reminders in that database (schema scripts in `deploy/postgres`). In PostgreSQL
mode written grain state, Session included, survives a restart. All streams go through one memory
stream provider, "game", in both modes, with ids built by `WildCat.Interfaces/StreamNames.cs` (the
"SMS" provider before step 1). No grain uses transactions; the 3.4.3 silo called
`UseTransactions()` anyway and the port dropped it.

## Flows

Session: client sends developer key and game key; `Developer.InitializeSession` checks the game
belongs to the developer, creates a Guid ticket and initializes `ISession(ticket)`, which starts
the idle clock; the gateway then calls `Touch()`. Login binds the user id to the session, sets
presence, starts the heartbeat timer. Every gateway request carries the ticket; for API calls
and relay traffic alike the gateway calls `TouchAndGetInfo()`, which throws if the session is
not initialized or has been idle for more than 60 minutes (`SessionExpiredException`; the
expired session clears its state), then refreshes `LastCallTime` and returns the developer key,
game key and user id that scope everything. Before step 4 the touch ran before the check, so
the expiry never fired on this path. Logout or disconnect ends the session. Before step 2 these
calls also counted API calls and relay messages and flushed the counts to `AccountingSystem` for
billing.

Matchmaking: the gateway calls `ICustomMatchMaker(gameKey, modeName).FindMatch(player, skill,
waitTime)`. The matchmaker loads its GameMode (or the default 2v2 mode), parks a
TaskCompletionSource per waiting player and every 3 s recomputes each player's criteria index
(the latest criterion whose start time has passed), times players out, and groups players whose
skill distance is within the current threshold, requiring MinPlayers-1 opponents when
`IsMinPlayersEnough` else MaxPlayers-1. On a match it creates `IRelayServerGame(Guid.NewGuid(),
gameKey)`, calls `StartGame`, and resolves every waiting task. The gateway's FindMatch handler
then joins the requesting player with `PlayerStarted` as an explicit step (the legacy gateway did
it under a TODO to make it not automatic; the SDK has no separate join message) and answers
with the match id and players. It caps the wait at 20 s so the matchmaker answers within the
30 s grain call timeout. Challenges bypass the matchmaker and create the game directly.

Relay: the backend never parses game payloads. `SendToAllBut(player, channel, bytes)` forwards
to every other InGame player via `IPlayer.SendDataToConnection`, which publishes a
`PlayerConnectionMessage` on the player's PlayerConnection stream; the gateway node
holding the socket is subscribed and writes the bytes out. Channel 0 carries system events
(player added, removed, rejoined, rejoin sync, property changed, game finished). Statuses:
Started, SomeJoined, AllJoined, SomeFinished, AllFinished, FinishedWithDisconnect. Disconnect
either finishes the game (`FinishGameWithOneDisconnect`) or marks the player Disconnected so
they can rejoin through `GetPendingMatches` and `RejoinMatch`.

Script events: a developer stores a C# method per event. `ScriptCompilationUtility` prepends a
generated call line and compiles with Roslyn (C# 12, globals type `Globals`). Since step 9:
`ScriptValidator` binds every node with the semantic model and rejects any type or member off
its whitelist (primitives, script-declared types, `WildCatScriptApi`, the leaderboard result
types, basic collections, LINQ, `StringBuilder`, `Math`, `Random`, message-only exceptions,
awaiting tasks) plus lock, async void, static fields, records, anonymous types, finalizers,
unsafe code and `#r`/`#load`; diagnostics come back as `ScriptDiagnostic` with lines relative
to the developer's script. `ScriptGuardRewriter` then inserts `ScriptGuard` calls into every
loop body, goto, method, lambda, accessor and instance field initializer, and wraps every
sequence handed to a library method or constructor (and every query expression source) in a
guarded enumerator, so a run stops itself with `ScriptTimeoutException` at its deadline
(`ScriptOptions.Timeout`, 3 s) and with `ScriptRecursionLimitException` before the stack runs
out. Scripts run on `ScriptWorkerPool`, a dedicated pool of threads, through `ScriptExecutor`,
which also refuses new runs of a game that has too many runs still going past their limit (see
bug 15 for what the guards cannot stop). Compiled scripts are cached per silo
by (game, event, script hash), bounded to 500 entries. Scripts get `args` (from the client,
untrusted) and a `WildCat` object (a `WildCatScriptApi`) with private data of the calling player
only, public data of any player (read only), time, leaderboard read/write (count clamped to 20),
inventory grants (`AddInventoryItems`, `SetInventoryItems`, at most 1,000,000 per item per
call), publisher data, and JSON helpers; each call checks that the session belongs to the
calling player and the event's game, and is marshalled back onto the grain scheduler.

## External dependencies

- PostgreSQL (step 5): Npgsql with the Orleans ADO.NET clustering, persistence and reminders
  packages, used when `WildCat:Orleans:Provider` is `PostgreSQL`; the connection string is
  `ConnectionStrings:WildCat`. The Orleans schema scripts are vendored in `deploy/postgres`.
  MongoDB, which the legacy Release build used, went away in step 1.
- SMTP: `SmtpEmailSender` (System.Net.Mail), from Player activation and password reset, set up
  under `WildCat:Email`. Without an SMTP host and sender address the host registers
  `LoggingEmailSender`, which logs the code instead. The legacy credentials were removed at copy
  time.
- Roslyn scripting: Microsoft.CodeAnalysis.CSharp.Scripting (5.0.0 since the port, 3.10 before).

Removed in step 2: PlayFab (`PlayFabAllSDK`; it backed PlayerStorage with entity files, set the
Player key format, validated provider logins and sent push notifications from TimedExecuter)
and CafeBazaar (receipt verification in IAPVerification). Nothing replaces either.

## Known bugs, ordered by severity

Security:
1. Fixed in step 4: `FrontEndServer.ProcessUserMessage` relayed the raw frame, including the
   sender's session ticket; relayed frames are now rebuilt without the ticket, payload unchanged.
2. Fixed in step 4: clients granted themselves items (Add/Set inventory) and set their own
   scores; the gateway now rejects 28, 111 and 113 with error 1, and scripts grant through
   `WildCatScriptApi.AddInventoryItems`, `SetInventoryItems` and `SetScoreInLeaderBoard`.
3. Removed in step 2: `Player.LoginWithProvider` never checked the returned PlayFab id and
   trusted other provider names; the whole provider login family is gone.
4. Fixed in step 4: `GetPublisherDataRequest_S` ignored the developer secret and
   `DeveloperStorage.Remove*` skipped it; the gateway now calls `GetStringForDeveloper`, the
   removes take the secret, and secrets are compared in constant time.
5. Fixed in step 4: `CreateNewAccountRequest` never checked the session and
   `CreateEnvironmentRequest` was unauthenticated; account creation now validates the session
   and the CreateEnvironment handler is gone (the host seeds developers and games from the
   `WildCat:Seed` configuration section, which replaced `devsconfig.json` in step 5).
6. Fixed in step 9: scripts could read and write any player's private data by id; private data
   is now limited to the player the script runs for, and the session must belong to that player
   and the event's game.
   Fixed in step 4: passwords (client MD5, then unsalted SHA1) now travel plain over TLS and
   are stored as salted PBKDF2-SHA512; activation and reset codes use `RandomNumberGenerator`;
   PlayerStorage no longer sets `TypeNameHandling.All` process wide, and PlayerInventory has
   its own grain storage (items survive reactivation). After review: the PBKDF2 work runs on
   the thread pool (`PasswordHasher.HashAsync`/`VerifyAsync`) instead of holding the Player or
   Developer grain for about 200 ms per call, and `IDeveloper.IsPasswordCorrect` is read only;
   the gateway limits sign-in requests (76, 78, 80, 82) per connection with a token bucket
   (`Gateway:AuthAttemptBurst`, `Gateway:AuthAttemptsPerMinute`); and the activation code, which
   used to stay in place after activation and also worked as a permanent password reset code,
   is now kept apart from the reset code, used up on success, expires after 30 minutes and is
   dropped after 5 wrong codes (no message re-sends an activation code yet).
7. Gateway: no origin check, `AllowedHosts *`, HTTPS redirection commented out, a fixed 2 MB
   reassembly buffer per connection that throws above 2 MB.
   Fixed in step 4 (limits and origins): `Gateway:MaxMessageBytes` (default 1 MiB) closes the
   socket with MessageTooBig, and `Gateway:AllowedOrigins` answers an unlisted Origin with 403
   (empty accepts any). `AllowedHosts *` and no HTTPS redirection stay on purpose: deployments
   override hosts, TLS terminates at the proxy, and the host honors forwarded headers.

Correctness:
8. Fixed in step 4: disconnect cleanup never ran (the connection entry was removed before the
   lookup, and an abrupt close skipped the callback); `ReceiveMessages` now always runs it, and
   `PlayerDisconnected` unsubscribes the player's streams, clears the player mapping only if it
   still points at this connection, and tells the player grain with that login's ticket.
   After review: a login and the disconnect cleanup of the same socket take a per-connection
   lock, so a socket that closes while a login is in flight no longer leaves that login bound
   to the dead socket (the login sees the socket gone and tells the player grain it
   disconnected); logging in as another player on the same socket tells the first player it
   disconnected; and `Player.Logout` ends its session only while that session is still bound
   to the player, since a socket that switches players keeps its session.
9. Fixed in step 4: `Session` was never persisted, so any deactivation or restart dropped every
   session; it now writes state on initialize, user binding and end, and touches at most once a
   minute.
10. `RelayServerGame`: a `Select` with side effects in the disconnect-finish path is never
    enumerated, so the other players stay InGame in a match that finished with a disconnect.
    Fixed in step 6b: the game mode is kept in state (`RelayServerGameState.Mode`; it lived in a
    field, so a reactivated match threw NullReferenceException on the next disconnect or finish);
    property setters, disconnects and finishes write state; the property size limit is counted
    from the stored values (a private running total that the JSON storage did not keep); a player
    property could never be set (the state replaced the whole dictionary and then threw
    KeyNotFoundException); the setters return false when a value does not fit instead of
    silently storing nothing; `GetPlayerData` throws `GameNotRunningException` ("You are not a
    player in this match.") for a player who is not in the match, and `PlayerFinished` looks the
    player up before changing the match state; setting a match property needs a player of the
    match; `PlayerRejoined` refuses a finished match instead of setting it back to SomeJoined.
11. `LeaderBoard.CreateList` indexes an empty list (any board with chunks fails to activate);
    partial chunks are never persisted; chunks are never cleared.
12. Removed in step 2: `DeveloperInvoiceCollection.GenerateInvoicesIfNeeded` looped forever;
    invoices are gone with billing.
13. Removed in step 2: `TimedExecutionManager` had broken DateTime keys and an A to B to A
    deadlock with the executer; the TimedExecuter subsystem is gone.
14. `RelayServerMatchMaker` (and the `MatchMaker` removed in step 2) uses `.Seconds`/`.Minutes`
    instead of `TotalSeconds` (waits capped at 60 s), never resolves the parked task on
    `RemoveDisconnectedPlayer`, and holds the grain call open longer than the 30 s response
    timeout. It also throws when the first criterion start time is not 0. Since step 6b the
    gateway caps a FindMatch wait at 20 s, so the call returns before the timeout.
15. Fixed in step 9: `ScriptCompilationUtility.RunScript` called `Thread.Abort`
    (PlatformNotSupported on .NET 5+; the port abandoned the thread, so a runaway script kept
    running), raced on a placeholder task so every call waited the full 3 s, kept a
    non-thread-safe static per-silo cache (multi-silo clusters got KeyNotFound) and ignored
    compile diagnostics. Scripts now stop themselves through the inserted guard calls, a fast
    run returns at once, the cache is thread safe and filled from the compiler grain on any
    silo, and compile errors reject the script. After review: library loops over sequences
    (`Enumerable.Repeat(1, int.MaxValue).Sum()`, `new HashSet<int>(sequence)`, query
    expressions) stop at the deadline too, because every sequence handed to library code is
    wrapped in a guarded enumerator; scripts run on a dedicated worker pool
    (`ScriptOptions.WorkerThreads`, one thread per processor by default) instead of the shared
    thread pool; and a game with more than `ScriptOptions.MaxOverdueRunsPerGame` (2) runs still
    going after their time limit gets `ScriptThrottledException` for new runs until they finish.
    Limits that remain: a single library call that neither calls back into script code nor
    reads a guarded sequence runs until it returns (huge allocations such as
    `new int[500_000_000]` or `new string('x', int.MaxValue)`, string operations on huge
    strings, sorting a large collection, passes over large in-memory collections), memory is not
    capped, and Roslyn script assemblies are never unloaded. Such a run holds one worker thread,
    never a thread-pool thread.
16. `Player.RejoinMatch` calls `game.PlayerRejoined`, which calls back into the same player.
    That worked on 3.4.3 only because call chain reentrancy was on by default there
    (`SchedulingOptions.AllowCallChainReentrancy = true`); Orleans 10 dropped the option, so the
    port restores it with `CallChainReentrancyFilter` until the cycles get targeted
    `RequestContext.AllowCallChainReentrancy()` calls. Since step 6b the gateway's RejoinMatch
    calls `PlayerRejoined` directly, which leaves no cycle on that path (`IPlayer.RejoinMatch`
    still has it). `SetEloScore` does not persist. (Step 2
    removed `CalculateELO`, which treated a draw as a loss, and `AddPlayerProvider`, which
    allowed one account per provider name.) Fixed in step 4: `Disconnected` ignored the login
    ticket, so a stale connection logged out a newer session; it now ignores a ticket that is
    not the current login's. A login on a new session also ends the player's previous session,
    whose ticket used to keep acting as the player until it idled out.
17. `PlayerInventory`: rollback copies a reference (no-op); `Unlock()` on the main inventory
    calls itself; `throw ex` loses stacks.
18. `PlayerFriendList`: `GetSentInvitations` returns received; `InvitationAccepted` calls
    `First` before its null check; `SetFriendStatus` throws on asymmetric lists and can fail
    logins. `PlayerChallengeHandler` never persists sends and accepts; two simultaneous
    challenges deadlock.
19. Removed in step 2: `PlayfabManager` had an endless retry loop ending in
    `Environment.Exit(1)`, a wrong ticket check and an unsafe HashSet; PlayFab is gone.
20. `NameToAccountIdMap.SetId` is never called, so name lookups always return null.
21. Gateway: LeaveGame response always throws (empty ticket assert); SessionRequired error goes to
    a stream nobody subscribes to; GetPlayerChallenges puts received into sent;
    `GetFriendsRequestMessage` deserializes into an empty array (the deserializers with null
    lists were card-game messages removed in step 2); `LogError(eventId, "text", exception)`
    everywhere loses stack traces; copy-pasted log messages; recursive retries with a 50 ms
    delay on non-idempotent operations; unawaited `OnDataReceived` so messages from one socket
    run concurrently and out of order. Fixed in step 4: the email activation and authenticate
    handlers call `Touch()` inside their try, so a bad ticket gets an error response instead of
    an escaping exception. After review, the SessionRequired error and every failed check of the
    header ticket (not a Guid, unknown, ended or expired session, no player logged in) are
    answered with an ErrorMsg on the connection, with the request id, instead of throwing out of
    the dispatcher and sending nothing; expected session errors are logged at Information
    without a stack trace. `SessionExpiredException`, `SessionNotInitializedException` and
    `InvalidGameException` moved from `WildCat.Grains/Session.cs` to `WildCat.Interfaces` so the
    gateway can catch them by type, and carry real messages. `RemoveInventoryItemRequest` looked
    the items up with `GetGrain<IInventoryItem>`, which two grain classes implement, so it threw
    every time; it now names the item class and answers error code 1 when the player does not
    hold the items instead of reporting success.
    Fixed in step 6: messages from one socket are handed to the dispatcher in order and every
    handler is awaited inside a try/catch (requests run concurrently, at most
    `Gateway:MaxConcurrentRequests` per connection; game messages are relayed in order by one
    worker per connection, without the relay's recursive retries); answers no longer copy the
    request header, which also fixes the LeaveGame answer; `GetFriendsRequestMessage` decodes
    its keys; the ported Session and Auth handlers log with the exception as the exception
    argument and answer unexpected exceptions with "Internal error" instead of the raw message.
    The rest (GetPlayerChallenges, the log calls and retries in the other groups) goes with
    roadmap step 6b.
    Fixed in step 6b for matches, leaderboards and inventory: the handlers answer expected
    failures with code 1 and a fixed text (unexpected ones with "Internal error"), LeaveGame
    without a game target gets an answer, the LeaveGame retries are gone, and FindMatch and
    LeaveGame answer on the connection instead of through the PlayerConnection stream.
22. Fixed in step 4: the gateway's default branch handed every message id without a handler to
    the relay, which forwarded it to the other players whenever it had a game target and a
    session. A match participant could therefore send ids up to `HighestInternal`, such as 10
    GameFinishedEvent, 128 MatchPropertyChangedEvent or a response carrying a guessed request

    `HighestInternal` are relayed now; any other unhandled id is answered with an ErrorMsg
